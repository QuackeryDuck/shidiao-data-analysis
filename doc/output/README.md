# 输出文档说明（doc/output）

本目录存放由 `engine` 生成的数据需求文档，格式为 UTF-8 Markdown。

- 默认输出：`doc/output/data_requirement.md`
- 示例输出：`doc/output/example_data_requirement.md`
- 生成命令：

```powershell
py -m engine.cli generate -i doc/input/research_brief.md -o doc/output/data_requirement.md
```

文档是**研究设计基线**，不是最终参赛稿。生成后应结合文献、问卷定稿、指导教师意见与实际数据条件修改。

## 1. 文档定位

数据需求文档回答“做分析之前必须先定下来的事”：

1. 研究问题如何落到可测量的变量？
2. 样本要多大、怎么抽、配额怎么分？
3. 每个问题用什么模型，为什么，前提是什么，备选是什么？
4. 要检验哪些假设，检验口径是什么？
5. 数据从哪里来，渠道如何组合？
6. 如何保证数据质量与过程可复现？

它不包含统计结果、结论或策略建议；这些属于后续分析报告。

## 2. 章节结构

| 章节 | 内容 | 使用建议 |
| --- | --- | --- |
| 标题与元信息 | 项目名、生成时间、版本 | 提交前核对项目名 |
| 0 文档摘要 | 研究设计一页纸、样本、核心方法、交付物 | 给评委或指导教师快速浏览 |
| 1 研究概述 | 背景、问题、目标、范围、概念框架、数据需求总览 | 确认问题与目标一致 |
| 2 研究假设 | 假设表、检验口径、探索性问题 | 补齐理论依据与文献 |
| 3 变量确定 | 变量总览、各角色变量、变量字典、量表、问卷结构、变量—模型映射 | 与问卷逐题对照 |
| 4 样本与抽样 | 总体、抽样方法、样本量、敏感性、配额、模型样本校验、采集规模 | 核对公式、参数与预算 |
| 5 模型与方法 | 选择逻辑、路线图、RQ—变量—模型对应、核心模型详解、前提、备选、软件模块 | 逐项确认前提与样本是否满足 |
| 6 调查渠道 | 渠道组合、执行表、二手来源、渠道质控、节奏、合规 | 核对可达性与成本 |
| 7 质量控制 | 六阶段质控、清洗规则、伦理、清单、验收标准 | 转成可执行的责任清单 |
| 8 数据交付 | 数据集结构、编码、缺失值、版本、交付清单 | 作为数据交接协议 |
| 9 进度与风险 | 周计划、分工、风险应对 | 与团队排期对齐 |
| 10 待确认事项 | 引擎默认值、推断项、需人工确认的假设 | **提交前必须逐条处理** |
| 附录 A | 本研究相关模型速查 | 答辩准备 |
| 附录 B | 方法学参考文献 | 按学校格式核对补充 |
| 附录 C | 术语表 | 统一团队用语 |

## 4. 写作与格式约定

- 标题层级：`#` 文档标题，`##` 章，`###` 节，`####` 模型条目。
- 表格：标准 GitHub Markdown 表格；长文本列放在最后，避免阅读时横向滚动。
- 公式：行内用 `` `n = z²P(1−P)/d²` ``，独立公式用代码块，便于复制到论文。
- 概念框架：使用 Mermaid `flowchart`；GitHub、Typora、VS Code 可直接预览。
- 数字：样本量取整、百分比保留 1 位小数；公式参数保留必要有效数字。
- 语气：陈述设计决策与依据，不使用“可能大概”等模糊表述；不确定处明确写“待确认”。
- 引用：方法学文献列在附录 B；正文提及时用“作者（年份）”或编号，按学校要求统一。

## 5. 如何审阅生成结果

建议按以下顺序，约 60–90 分钟完成一轮审阅：

### 5.1 研究问题与假设

- [ ] 每个 RQ 都能在假设表或探索性问题中找到落点。
- [ ] 假设的方向、变量、检验方法一致。
- [ ] 中介/调节假设的路径完整（IV → M → DV；W × X → Y）。
- [ ] 理论依据不是套话，能对应到具体文献。

### 5.2 变量

- [ ] 每个核心构念有操作化定义、题项数、量表与测量层级。
- [ ] 因变量与 RQ 的结果词一致。
- [ ] 控制变量有纳入理由，不是越多越好。
- [ ] 筛选变量与质控题不会误删有效样本。
- [ ] 问卷题项能覆盖变量字典中的每个字段。

### 5.3 样本

- [ ] 目标总体、抽样框、调查单位清晰。
- [ ] 样本量公式参数与输入一致。
- [ ] 有限总体修正、设计效应、有效回收率的用法正确。
- [ ] 分层配额合计 100%，且每层可达。
- [ ] 每个核心模型的最低样本要求都满足。

### 5.4 模型

- [ ] 5.3 的每个 RQ 至少有一个主模型。
- [ ] 5.4 的“对应研究问题”和“涉及变量”没有错配。
- [ ] 模型前提（正态、方差齐性、共线性、样本量、类别频数）可检验。
- [ ] 不满足前提时有明确备选，而不是删数据。
- [ ] 高阶模型有降级方案，本科生团队能执行。

### 5.5 渠道与质控

- [ ] 渠道能触达目标总体，配额与渠道能力匹配。
- [ ] 线上/线下比例、投放节奏与周期、预算一致。
- [ ] 无效问卷规则可操作，阈值有依据。
- [ ] 质控责任能落到人，检查点有时间。
- [ ] 文本数据与二手数据有授权/合规说明。

### 5.6 交付

- [ ] 数据集结构覆盖分析所需全部字段。
- [ ] 编码表、缺失值规则、版本命名可直接执行。
- [ ] 第 10 章待确认项已逐条关闭或明确标注。

## 6. 常见修改

### 6.1 删减模型

核心模型建议 6–12 个（纯问卷通常 6–10 个）。删减时同步修改：

1. 5.1 方法选择逻辑中的理由；
2. 5.3 RQ—变量—模型对应表；
3. 3.10 变量—模型映射；
4. 5.5 前提检验清单；
5. 8.1 数据集结构（不再需要的字段可保留，但标注备用）。

### 6.2 调整样本量

修改输入 frontmatter 中的 `confidence_level`、`margin_error`、`expected_proportion`、`population_size`、`design_effect`、`response_rate`，重新生成。不要只手改第 4 章数字，否则与敏感性分析和模型校验不一致。

### 6.3 增加变量

在输入的核心构念表中增加一行，重新生成；然后手工检查：

- 新变量是否进入假设与模型；
- 题项数是否影响问卷长度；
- 是否增加回归自变量数量，从而触发样本门槛变化。

### 6.4 保留团队已有假设

在输入中增加 `## 研究假设` 章节。引擎会保留原文，并补齐变量、方法与理论绑定。

### 6.5 输出到其他文件

```powershell
py -m engine.cli generate `
  -i doc/input/research_brief.md `
  -o doc/output/campus_coffee_data_requirement.md
```

建议文件名包含项目短名与版本，如 `campus_coffee_v2_data_requirement.md`。

## 7. 版本与归档

- 每次实质修改输入后重新生成，不直接覆盖唯一版本。
- 建议保留：`data_requirement_v1.md`、`data_requirement_v2.md`，并在文首记录变更。
- 提交版另存到 `report/`，与问卷、数据字典、分析代码一起归档。
- 若团队使用 Git，输出文档可入库；原始数据与含个人信息的数据不要入库。

## 8. 已知限制

- 自动生成的假设与变量绑定基于关键词和规则，中文歧义可能导致错配。
- 模型推荐偏保守，可能同时给出多个可接受方案；需要团队做最终取舍。
- 样本量按简单随机抽样公式计算，复杂设计仅通过设计效应近似。
- 渠道库以通用场景为主，特定平台的最新政策需自行核实。
- 参考文献为方法学通用条目，不替代文献综述。
